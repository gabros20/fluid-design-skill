# fluid-design: a review of the system (September 2026)

What this reviews: the fluid scale at the centre of the `fluid-design` skill. That is
`--fluid = max(0.58px, min(100svh/900, 100vw/1440))` from 1024px up, with the two damped type
units, the chrome unit, the Tailwind v4 `fluid-*` utilities, the generator, audit and verifier,
and how all of it holds up in day-to-day creative website builds.

How it was reviewed:
- read the skill and the Eagle source docs (`docs/FLUID-SCALE.md` and the 2026 motion-engine
  panel in `.orchestrate/reports/`)
- read the two test builds' `SKILL-FEEDBACK.md`
- surveyed 7 agent skills (found with `npx skills find` on skills.sh, SKILL.md files read from
  GitHub) and 11 libraries and methodologies
- measured style and layout cost in Chromium with 1500-element test pages
- modelled browser zoom numerically

Raw evidence is in `docs/review-2026-09/`:
- `prior-art.md`: the field survey
- `support-perf.md`: browser support and the benchmarks
- `perf/`: the harness and raw numbers
- `zoom*.mjs`: the zoom model

---

## 1. Verdict

**This is the strongest system in its niche, and it has one serious blind spot.**

For what it is built for, a design-led marketing or editorial site that has to look like the
Figma frame on a 13" laptop, a short browser window and a 5K display, nothing in the field comes
close. It is the only system found anywhere that puts viewport **height** into the same scale
as width. It is the only one with damped type units derived from a shared base unit. It is also
the only one that ships a generator, a static audit and a viewport-matrix verifier.

It is weak on three things:
1. **Browser zoom.** Pure viewport units cancel desktop zoom, and on big monitors zoom does
   nothing until the layout falls through to mobile.
2. **The JavaScript bridge.** Motion code that needs scaled *distances* has no first-class way
   to read the unit.
3. **Everything below 1024px.** Tablet and mobile get no fluid behaviour at all.

| Dimension | Score | One line |
|---|:-:|---|
| Design fidelity (matching the frame) | ★★★★★ | Pixel-exact at the reference, proportional everywhere, one screen tall when height binds |
| Performance | ★★★★☆ | Zero JS, no cost while scrolling; resize is 30% of a frame at realistic density, and cheaper than per-declaration `clamp()` |
| Developer experience | ★★★★☆ | The Figma number *is* the class (`lg:fluid-py-120`); the costs are dual authoring and a few sharp traps |
| Flexibility | ★★★☆☆ | Strong from 1024 up; flat below it; one scale per page by design; few utility families |
| Browser support | ★★★★★ | Nothing newer than Tailwind v4's own floor (Safari 16.4 / Chrome 111 / Firefox 128) |
| Accessibility | ★★☆☆☆ | Fails WCAG 1.4.4 (resize text) on displays wider than ~1440 between 100% and 150–250% zoom |
| GSAP / Motion interop | ★★★☆☆ | No property collisions, and documented; but no runtime API for scaled distances in JS |
| Verification and tooling | ★★★★★ | Generator with `--check`, 11-rule audit, matrix verifier, calculator, stale-CSS probe |
| As an agent skill | ★★★★★ | Deeper than every skill surveyed; the rules carry their measured reasons |

## 2. The field: how it compares

| System | Mechanism | Uses height | Upper cap | Zoom / a11y | Tooling |
|---|---|:-:|---|---|---|
| **fluid-design (ours)** | `N × unit`, unit = `min(svh, vw)` ratio | **yes** | none by default (`ceiling` optional) | pure viewport units above 1024: **zoom cancelled** | generator, audit, verifier, calc, probe |
| Utopia | `clamp(minRem, rem + vw, maxRem)` per step | no | yes | rem-anchored; flags WCAG violations per step | calculator, `utopia-core` |
| fluid-tailwind (barvian, 1.8k★) | `~` modifier → `clamp()` between breakpoints | no | yes | **compile-time `checkSC144` WCAG 1.4.4 check** | the only a11y linter in the field |
| tailwind-clamp, tailwindcss-fluid-type | `clamp()` arbitrary values or config | no | yes | none | plugin only |
| Open Props / Every Layout | `clamp(min, Nvw, max)` tokens and recipes | no | yes | none formal | none |
| Agency vw-root (Lumos, Osmo, `html{font-size:calc(100vw/1440*10)}`) | root font-size in vw, everything in rem | no | usually a frozen breakpoint | zoom mostly cancelled, same class of problem as ours | Webflow builders |
| postcss-px-to-viewport | build-time px → vw and px → vh, **separately** | on separate axes, not combined | none | flagged as zoom-hostile | PostCSS plugin |
| Finsweet Client-First | rem plus root font-size per breakpoint; **rejects vw/vh on purpose** | no | yes | "browsers can zoom normally" is its selling point | Webflow generator |

Agent skills: the top install counts (`wshobson/responsive-design` at 19k,
`jakubkrehel/better-typography` at 23k) are generic `clamp()` reference cards or typography review
checklists. `kemiljk/fluid-design` shares our name but is a motion-physics skill. The most rigorous
skill found, `impertio-studio/frontend-impl-responsive-layout-fluid` (1★), hard-codes "max ≥ 2×
min per WCAG 1.4.4" and rem-only type. **No skill or library found combines height and width into
one scale.**

Three things we should take from the field:
1. **fluid-tailwind's `checkSC144`**: a build-time zoom and resize check. Nothing we ship does this.
2. **Utopia's split**: type keeps a rem-anchored component, space may be pure viewport units.
   That is the standard answer to the zoom problem.
3. **better-typography's review format**: severity levels and a Block/Approve gate, which our
   audit output could adopt.

## 3. Design fidelity: ★★★★★

What it gets right:
- **Contain fit on both axes** (`min()`): a composition can never outgrow the window. When
  height binds, a section drawn 900 tall is exactly `100svh`. Measured on the reference build, a
  width-only system turns a 3-line heading into 7 lines at 1024×900; ours holds 4.
- **The reference is a viewport (1440), not the canvas (1680).** This is counter-intuitive but
  correct, and it was rejected twice for good reasons (`fluid-scale.md` §4). The cost is a
  1280px content budget, which `calc.mjs budget` and `cqw` handle.
- **Damped type units** shrink type slower than layout below the reference, and grow it with the
  layout above, so wrap points hold above 1440 by construction. The floors are derived at
  `engageAt`, so the handover to mobile is continuous for type.
- **Large displays get a larger drawing**, not a small frame stranded in empty space.

What to watch:
- **When width binds, one-screen sections come out shorter than the window** (640px tall at
  1024×900). This is documented and fine over a pinned render, but on a plain section it reads
  as a gap to the next section.
- **The type floors engage at f ≈ 0.70** while layout continues to 0.58, a knee that shows only
  under about 640px tall. Documented.
- **Raster assets upscale about 1.3–1.6× on 5K.** No ceiling is the default; `performance.md`
  covers image `sizes` for a growing page.

## 4. Performance: ★★★★☆

**Runtime cost while scrolling: zero.** It is pure CSS. The units recompute on resize only, and
`svh` is inert to the iOS toolbar. No JS, no `ResizeObserver`, no layout thrash during scrolls or
scroll-driven scenes.

**Resize cost** was measured in Chromium 153: 1500 elements, 4 sizing declarations each, a
21-step sweep, per-step main-thread task time (budget is 16.6 ms per frame):

| Variant | Width sweep | Height sweep |
|---|--:|--:|
| Literal px (no viewport awareness) | 0.56 ms | 0.14 ms |
| **Ours, shared utility classes (realistic)** | **5.07 ms** | **4.72 ms** |
| Utopia-style `clamp(…vw…)`, shared classes | 9.22 ms | 0.69 ms |
| Ours, 1500 unique per-element rules (worst case) | 16.06 ms | 14.05 ms |
| `clamp`, 1500 unique rules | 12.30 ms | 2.98 ms |

What the numbers say:
- **At realistic density ours costs about 30% of a frame per resize step, and is cheaper than
  per-declaration `clamp()`** (about 1.9× less layout work). "Just use clamp" is not a
  performance win.
- **Sharing matters about 9×.** Spend the unit through a small set of reused utility classes,
  never through unique inline `calc()` per element (for example CSS-in-JS generating one rule per
  instance). This belongs in `performance.md` as a rule.
- **The height arm has a real cost on height-only resizes** (4.7 ms per step, where a width-only
  clamp costs 0.7). In practice that only happens on a desktop window drag or a fullscreen
  toggle, because `svh` does not move with the iOS toolbar. Acceptable by design.
- **First layout is unaffected** (25 ms in every variant).
- **Subpixel:** fractional widths such as 52.922px produced **no seams** in Chromium at DPR 1 and
  2, in flex rows of adjacent tiles, checked in both geometry and pixels. Still untested: Safari,
  Firefox, and adjacent boxes on separate compositor layers (for example one tile with `translate`
  or animated by an engine). That is the plausible seam case.

**Suggested experiment.** Register the unit as a typed property:
`@property --fluid { syntax: '<length>'; inherits: true; initial-value: 1px }`. The computed
value then becomes a resolved px length rather than a token stream re-evaluated in every
consumer, which may cut the recalc share. It also gives JavaScript a readable number (§8). One
catch: `probe.mjs` and the Eagle `CLAUDE.md` check compare the unit's formula *string*, so they
would need a sentinel property instead. Benchmark it before adopting.

## 5. Developer experience: ★★★★☆

What works well:
- **The Figma number is the class**: `lg:fluid-py-120`, `lg:fluid-display-64/72`. There is no
  min/max pair per property to keep in sync. That is the maintenance failure of every
  `clamp()`-per-token system, and ours removes it.
- **Deterministic artifacts.** One `fluid.config.json` drives Tailwind v4, CSS, SCSS, StyleX and
  TS outputs, and `--check` catches drift. The audit catches the silent killers:
  - a length multiplied by the unit
  - px tracking
  - mixed px/rem breakpoints
  - unscaled `auto-fill` minimums
  - px values at the engage breakpoint
- **`cn.ts` registers the fluid families with tailwind-merge**, so overrides resolve.

What costs time:
- **Every drawn value is written twice**, `py-16 lg:fluid-py-120`, because mobile values differ
  and are not scaled. This is the largest day-to-day tax (see §9, the mobile arm).
- **Silent failure modes that compile clean.** The audit catches most of them, but only fully
  on the Tailwind stack. On SCSS and vanilla it is "close to blind" (test build B, finding 11):
  - `64px * var(--fluid)` drops the declaration
  - a partial px breakpoint ladder reorders `sm:` over `lg:`
  - overriding `--fluid` on a section does not re-derive the type units
- **Stale stylesheets after a dev-server restart** look exactly like a code bug. The probe and
  docs cover it well, but it is a recurring cost of `@utility` families.
- **Utility coverage is thin by design:** 34 families.
  - Missing: negatives (you write `lg:top-[calc(-8*var(--fluid))]`), logical properties
    (`ps/pe`, `inset-inline`), `basis`, `scroll-mt`, `space-x/y`, and radii.
  - Each omission is defended for Eagle, a square-cornered site with about 14 negatives. For
    creative work, rounded cards and RTL are common. The generator could emit these behind
    config flags at almost no cost.
- **Tailwind IntelliSense** does not suggest numbers for bare-number functional utilities, so
  authors type from the design file. That is fine, but it is not discoverable.

## 6. Flexibility: ★★★☆☆

It is strong where it applies. The limits:

| Need | Supported? |
|---|---|
| A site drawn at another frame (1600/64, ceiling 1.6) | Yes, via config (proved by test build B) |
| Document-style pages (docs, blog) | Yes: `heightAxis: false` gives a width-only unit |
| A new role (UI, captions) | Yes: one damping line |
| A section drawn taller than 900 fitting one screen | **No, on purpose** (one scale per page; §10 explains why re-anchoring was removed) |
| Tablet 768–1023 | **Flat.** A tablet landscape in desktop layout starts at 1024 at f = 0.71 |
| Mobile fluid (375/390 reference) | Offered in preflight but **never validated**; no generator support |
| Per-component (container-relative) scaling | Only through `cqw` rows; the unit itself is viewport-only |
| Over-budget rows (drawn wider than 1280) | `cqw` recipe plus the `calc.mjs budget` suggestion |
| Large-screen restraint | `ceiling` (which also caps chrome) |

The biggest flexibility gap for creative work is the **missing mobile arm**. See §9, where it is
also the biggest DX win.

## 7. Browser support: ★★★★★ (with one historical asterisk)

| Feature | Chrome | Firefox | Safari |
|---|---|---|---|
| `min()`/`max()`/`clamp()` | 79 | 75 | 13.1 |
| `svh`/`lvh`/`dvh` | 108 | 101 | 15.4 |
| Container query units (`cqw`) | 105 | 110 | 16 |
| `@property` | 85 | 128 | 16.4 |
| **Tailwind v4 floor, which binds the whole stack** | **111** | **128** | **16.4** |

- **Nothing in the fluid layer raises the floor above Tailwind v4's own.**
- **Asterisk:** iOS Safari **16.4–17.3 computed `svh` like `dvh`** when the tab bar hid (WebKit
  bug 261185, fixed in 17.4, March 2024). The "svh does not move while you scroll" invariant has
  only really held since iOS 17.4. That window is tiny in late 2026, but `ios-safari.md` should
  state it so nobody chases a ghost on an old device.
- **A fallback needs `@supports`, not declaration order.** A second `--fluid` declaration always
  wins in the cascade, whether or not the browser supports `svh`, because custom properties are
  not type-checked at parse time. If the floor ever drops below Safari 15.4, use
  `@supports (height: 100svh) { :root { --fluid: …svh… } }` over a `vh` default.
- **Doc fix:** `stacks.md` says a rem breakpoint would "disagree at any zoom other than 100%".
  Zoom does not change px-versus-rem media queries. The browser's **default font-size setting**
  does. The argument still holds, but the reason given is wrong.

## 8. Accessibility: ★★☆☆☆ (the main finding)

**Desktop browser zoom (Cmd/Ctrl +) is cancelled by viewport units.** Zoom makes CSS pixels
bigger and shrinks the CSS viewport by the same factor. A length computed from `vw`/`svh` shrinks
by exactly that factor, so it renders at the same physical size. Our unit is 100% viewport-derived
above 1024px (there is no rem or px term). Text does not grow until zoom pushes the CSS viewport
below 1024 and the page falls through to the flat mobile CSS.

Modelled, body text size relative to 100% zoom (`docs/review-2026-09/zoom.mjs`):

| Display | 125% zoom | 150% | 200% | Where text starts growing |
|---|--:|--:|--:|---|
| 1440×900 | 117% | 150% (mobile) | 200% (mobile) | about 141% |
| 1920×1080 | 103% | 117% | 167% (mobile) | about 188% |
| 2560×1440 | 100% | **100%** | **117%** | about 250% |

- WCAG 1.4.4 asks for text resizable to 200%. **We fail it on any display wider than about 1440
  CSS px.**
- The failure is worst on exactly the large monitors the system is proud of.
- The headings behave oddly too: at 1440, 150% zoom *shrinks* the heading to 94%, because the
  mobile heading is smaller than the scaled desktop one.

`typography.md` and `fluid-scale.md` §12 describe "ignores the browser font-size setting" as
deliberate. **That is a different setting from zoom, and zoom is not mentioned anywhere in the
skill.** The docs as written would lead an agent to wave this away.

The fix options, ranked:

1. **Say it plainly in the skill** (`fluid-scale.md` §12, `typography.md`, preflight).
   Accessibility-sensitive clients (public sector, EU EAA, anyone with a WCAG AA obligation)
   should hear about it in preflight.
2. **An opt-in zoom compensation.** A few lines of JS set `--zoom` from
   `outerWidth / innerWidth` (or `devicePixelRatio` against a baseline captured at load), and the
   unit becomes `calc(min(…) * var(--zoom))`. That restores 1:1 zoom response.
   - Caveat: side panels and devtools skew `outerWidth`.
   - Unverified in Safari. Prototype it and test it before promising anything.
3. **A damped-upward type option** (`copy = 0.33·f + 0.67px` at every f, which gives the px term
   a zoom-responsive share). This gets body text to 128% at 150% zoom and 156% at 200% on 2560
   (`zoomB.mjs`). It is partial, and it gives up "wraps match the frame above the reference",
   which the system chose for good reasons. Offer it as a config switch, not a default.
4. **A zoom check in `verify-matrix`.** Emulate zoom (viewport ÷ z, deviceScaleFactor × z) and
   assert body text grows at least 1.5× at 200%. This is our version of `checkSC144`, and it
   makes the trade visible on every project.

Other a11y points are in good shape:
- Pinch-zoom on mobile works (the unit is flat below 1024).
- `ios-safari.md` correctly refuses `maximum-scale=1`.
- Reduced motion lives in the companion skill.

## 9. Working with GSAP and Motion: ★★★☆☆

**What is solid.** The layers do not collide. The scale writes `font-size`, `padding`, `gap`,
`width` and `height`, and only on resize. Engines write `transform` and `opacity` per frame.
`fluid-translate-*` writes the independent `translate` property so it composes with an engine's
`transform`. Pinned scrub scenes were verified at 700 and 900 tall with identical frames at
identical progress. The Eagle 2026 engine panel also settled the Motion-versus-GSAP question
for that site (Motion, no Lenis, no ScrollTrigger pin near `<video>`), and the scroll-animation
skill now carries a coexistence guide for sites that already have GSAP or Lenis.

**What a creative build hits within a day.** Entrance offsets of 24–40px are fine as fixed px.
Creative work animates *large* distances: a product flying across the hero, a horizontal gallery
track, a marquee speed, a ScrollTrigger `end: "+=1800"`, a Flip between two scaled layouts. The
tables below show what goes wrong and the pattern to use; the skill documents none of them today.

**GSAP**

| Situation | Problem | Pattern |
|---|---|---|
| `x: 600` | Correct only at 1440; 1.6× too short at 2560 | `x: () => 600 * fluidPx()` plus `invalidateOnRefresh: true` |
| `end: "+=1800"`, `start: "top 120px"` | Travel and offsets do not scale | Function values `end: () => "+=" + 1800 * fluidPx()` |
| Horizontal track | Track width changes with the unit | `x: () => -(track.scrollWidth - innerWidth)` with `invalidateOnRefresh` (layout-measured, so it scales for free) |
| SplitText lines | Fluid type re-wraps on resize, so line splits go stale | `autoSplit: true` with `onSplit()` returning the tween (GSAP 3.13+), or authored hard breaks |
| Flip | Measures real boxes | Works as is |
| Breakpoints | Duplicated literal | `gsap.matchMedia()` with the generated `ENGAGE_QUERY` |

**Motion**

| Situation | Problem | Pattern |
|---|---|---|
| `useTransform(p, [0,1], [0, 600])` | Same fixed-px problem | Map to a unitless progress and let CSS scale it: `style={{ '--p': p }}` plus `translate: calc(var(--p) * 600 * var(--fluid)) 0` |
| `layout` / `layoutId` | Measures real boxes | Works as is |
| Values needed as numbers | No API | a `useFluid()` MotionValue fed by a resize listener |

The **CSS-variable pattern** (the engine tweens a unitless `--p`, and CSS multiplies it by the
unit) is the most useful idea here. It works with any engine, stays correct live through a resize
with no refresh, and needs no JS maths. Cost: a style recalc on one element per frame. Scope the
variable with `@property --p { inherits: false }` to keep that recalc from spreading to
descendants.

**What is missing is a runtime API.** The only JS reader today is a probe element inside the
scroll well, because `getPropertyValue('--fluid')` returns the formula string. Ship a
`fluid.runtime.ts` from the generator (`--stack ts`):
- `fluidPx(n?, unit?)`: reads a registered `@property`, or a cached probe
- `onFluidChange(cb)`
- `ENGAGE_QUERY`, already emitted

Also ship a GSAP and a Motion recipe page in the scroll-animation skill (§ fluid-interop).
Together these turn "entrance offsets stay fixed px" into a complete answer.

Canvas, WebGL and Three.js: the renderer sizes from its container, which is fine, but text and
UI drawn in the canvas need `fluidPx()` too. The same runtime helper covers them.

## 10. Day-to-day creative build questions

| Question | Answer today |
|---|---|
| Designer hands over a 1440 or 1920 frame instead of 1680? | Config: canvas and gutter change; the reference stays a viewport (1440×900). A 1920 canvas means a 1280 content budget over a 1920 drawing, so tell the designer early |
| Designer draws mobile at 390? | Mobile is hand-authored, with no scale. The biggest gap; see the mobile arm below |
| CMS copy longer than the design (German, French, client edits)? | Text measures are fixed and display type is damped, so wraps grow and nothing overflows horizontally. One-screen sections can then overflow vertically; use `fluid-min-h`, not `fluid-h`, where copy is editable |
| RTL or logical properties? | No `ps/pe/ms/me` fluid families. Add them to the generator |
| Rounded cards, scaled radii? | Off the scale by choice. Add an opt-in `fluid-rounded-*` |
| Dark mode or themes? | Orthogonal; tokens-and-theming covers the traps (`dark:` without a custom variant) |
| Full-bleed video and images? | Covered (`media.md`: `sizes` for a growing page, posters, inline SVG) |
| Sticky and pinned sections? | Covered (`overflow-x: clip`, no transformed ancestors, pins in `lvh`) |
| 4K and 5K? | Grows as one drawing; set `ceiling` if the rasters are not about 3000px wide |
| Print? | Not addressed; the units are 1px in print (below the breakpoint), so print gets mobile CSS. Fine, but unstated |
| Existing site with a vw root font-size (agency pattern)? | Brownfield migration removes competing ladders per section; the vw-root pattern should be named explicitly as one of them |

### The mobile arm: the single biggest upgrade

Below `engageAt`, set the unit to a width-only phone scale, for example
`--fluid: clamp(0.85px, 100vw/390, 1.25px)`. The unprefixed utility then **is** the mobile drawn
value, and `lg:` swaps in the desktop one:

```html
<section class="fluid-py-48 lg:fluid-py-120">
```

- It halves the "write it twice in two units" tax: both values come from their frames.
- It scales between the 375 and 430 phones and across the 768–1023 tablet band (clamped), where
  today everything is frozen.
- Mobile keeps partial zoom response through the clamp.
- It needs generator support, a mobile verification row (the phones are already in the matrix)
  and one real validation build before it becomes a default.

## 11. Verification and tooling: ★★★★★

- **The generator is deterministic** (`--check`, 3 fixture configs covering a ceiling,
  width-only and chrome-off).
- **The audit has 11 rules and 27 self-tests.**
- **`verify-matrix` checks:**
  - overflow and the unit maths
  - one-screen fit and grid column counts
  - 5 widths × 5 heights, plus phones
  - screenshots
- **`probe.mjs`** diagnoses a stale stylesheet in one shot.
- **`calc.mjs`** gives factor tables and budget checks.

Nothing else in the field comes close. Gaps:
- **Stack coverage:** the audit only sees Tailwind class strings for its core rule
  (`fixed-px-at-engage`). SCSS and vanilla blocks inside the engage query are invisible to it.
- **No zoom row** in the matrix (§8).
- **No non-Chromium run.** `verify-matrix` could accept `--browser webkit` (Playwright WebKit) to
  cover the Safari rendering questions (seams, SVG) before a device is needed.
- **Report format.** Audit output could adopt a Block/Approve severity gate, borrowing
  better-typography's format.

## 12. Recommendations, prioritised

**P0: correctness and accessibility**
1. Document the zoom behaviour honestly in `fluid-scale.md` §12, `typography.md` and preflight
   (ask "does this site carry a WCAG AA obligation?"). Fix the zoom and font-size confusion in
   `stacks.md`.
2. Add a zoom row to `verify-matrix` (assert body text grows at least 1.5× at 200%), as a warning
   by default and an error when `a11y.zoom: "strict"`.
3. Prototype the opt-in `--zoom` compensation, test it in Chrome, Safari and Firefox, and ship it
   as `assets/styles/shared/zoom.ts` only if it holds.

**P1: creative-build capability**

4. Ship `fluid.runtime.ts` (`fluidPx`, `onFluidChange`) and register `--fluid` as `@property
   <length>` (benchmark it first; migrate `probe.mjs` to a sentinel).
5. Add GSAP and Motion "scaled distances" recipes to the scroll-animation skill's
   `fluid-interop.md`: function values with `invalidateOnRefresh`, the `--p` pattern, SplitText
   `autoSplit`.
6. Design, build and validate the mobile arm as a config option (`mobile: { reference: 390,
   clamp: [0.85, 1.25] }`).
7. Opt-in utility families: negatives, logical properties, `basis`, `scroll-mt`, `rounded`.

**P2: polish**

8. `performance.md`: "spend the unit through shared classes; unique per-element `calc()` costs
   about 9× in recalc" (measured).
9. `ios-safari.md`: note that `svh` behaved like `dvh` on iOS 16.4–17.3.
10. Extend the audit to SCSS and CSS blocks inside the engage query.
11. `verify-matrix --browser webkit`.
12. Name the agency vw-root-font-size pattern in `brownfield-migration.md` as a ladder to remove.

   - It warns by default; `--zoom-strict` makes it gate the run.
3. **Compensation shipped, with a better formula than the review proposed.**
   - The review's `calc(min(…) * var(--zoom))` on the whole unit would have pushed the layout past
     the zoomed viewport. Multiplying the whole *type* unit double-counts its px term.
   - The shipped version multiplies only the `--fluid` *base* inside the display and copy units.
     That gives back the exact unzoomed CSS value, so text zooms 1:1 and layout keeps fitting.
   - `assets/runtime/fluid-zoom.js` detects zoom by requiring `outerWidth/innerWidth` and
     `devicePixelRatio` to agree, and falls back to 1 otherwise. It retries on the next frames
     because `outerWidth` reads 0 before the first frame.
   - Config key `zoomCompensation`, default `true`.
   - Results on `pizza-next`: 125/150/200% zoom gives 125/150/200% text on a 2560 window, and 125/150% on 1920,
     where it was 100–124% before. The full matrix still passes.
   - Open: Safari and Firefox are unverified. The mobile-handover step on wide windows remains,
     and the mobile arm (P1) would close it.
