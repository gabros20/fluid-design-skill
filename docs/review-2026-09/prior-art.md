# Prior art: fluid typography/design systems and agent skills, vs. our `fluid-design` system

Our system, one line: above 1024px, every drawn px is `N * var(--fluid)`, where
`--fluid = max(0.58px, min(100svh/900, 100vw/1440))` — tracks width AND height
(tighter wins), 1px at 1440×900 reference, no ceiling (unbounded upward), two
damped type units for gentler shrink below reference, Tailwind v4 `@utility
fluid-*`, mobile <1024 is flat per-breakpoint CSS (not on the scale at all).

## Part 1 — Agent skills (skills.sh ecosystem)

Fetched and read SKILL.md + references directly from GitHub for 7 candidates.

**kemiljk/fluid-design@fluid-design** (github.com/kemiljk/fluid-design, 6★, pushed 2026-03) — **name is a false friend**: despite matching our skill's name almost exactly, its actual content is "10 Principles for Fluid *Interfaces*" — spring physics, gesture/drag interruptibility, shared-element transitions, `layoutId`, View Transitions API. It is a **motion/physics skill, not a typographic scaling skill**. Zero mention of clamp/vw/viewport scaling. Not relevant prior art for our system despite the name collision.

**wshobson/agents@responsive-design** (39,911★ repo, plugin path `plugins/ui-design/skills/responsive-design`) — solid generalist skill: mobile-first, container queries, `clamp()` type/space scales with the standard slope-formula generator (`fluidType({minFontSize, maxFontSize, minViewport=320, maxViewport=1200})`), fluid `min()`-based container widths, auto-fit grids. Width-only. No height-awareness, no Tailwind-plugin integration (raw CSS), no a11y section, no verification step, no tooling beyond a JS snippet in the doc. Depth: solid breadth, shallow on any one topic — a reference doc, not an enforced system.

**jakubkrehel/skills@better-typography** (7,094★ repo) — broadest and most a11y-literate of the set, but *not* primarily about fluid/viewport scaling — it's a typography **review checklist** (scale, line-height, letter-spacing, wrapping, iOS input zoom, verification/reporting format with severity levels and a before/after table). Its `spacing-and-sizing.md` explicitly recommends **fixed rem type scales**, not viewport-fluid ones. Its accessibility section states plainly: "Typography must survive the reader changing it: zoom, a larger browser font size" — i.e., its philosophy is the opposite of ours (respect user font-size; we deliberately don't above 1024px). Has a real verification/reporting protocol (severity, Block/Approve gate) that none of the other skills have — the most rigorous *process*, even though it isn't the most fluid-scaling-specific.

**patricio0312rev/skills@responsive-design-system** — near-identical boilerplate to wshobson's: `clamp()` scale tables, Tailwind config `fontSize` extension, container queries, grid recipes. Width-only, no a11y section, no tooling, no verification. Shallow — reads like a generated reference card.

**lvtd-llc/skills@responsive-layout-math** (1★, plugin `web-design-math/skills/responsive-layout-math`) — the only skill with an explicit "derive, don't guess" framing and multi-file structure (`knowledge.md`/`rules.md`/`patterns.md`/`examples.md`/`checklist.md`/workflow). Correctly distinguishes `vw/vh` vs `sv*`/`lv*`/`dv*` variants and states the rule "avoid `100vh` for mobile full-height UI." But this height-unit knowledge is scoped to **single-axis hero-height sizing**, never combined with width in a shared scale formula. Sourced from a book (*Math for Web Design*, ch. 6) with citation tracking — unusually well-documented provenance for a skill, but thin on live tooling (no scripts, no verification step, no Tailwind integration).

**impertio-studio/frontend-design-claude-skill-package@frontend-impl-responsive-layout-fluid** (1★, pushed 2026-09-15) — **the deepest and most current skill found**. Explicit decision trees (`svh` vs `lvh` vs `dvh` vs `vh`, container query vs media query, mobile- vs desktop-first), MDN citations with verification dates (2026-05-19), and a hard accessibility rule baked into the spec itself: **"MAX MUST be at least 2× MIN per WCAG 1.4.4"** and "font-size in `rem`, NEVER `px`." It correctly separates `svh`/`lvh`/`dvh` semantics (URL-bar-visible / hidden / dynamic) but — like every other skill — never combines height with width in one fluid-scale formula; height units are reserved for full-bleed heroes only. Most rigorous single-source-of-truth skill in the set, closest in spirit to a "deterministic rule set" but still narrower in scope (no motion, no damped-unit concept, no Tailwind utility generation).

**dylantarre/design-system-skills@responsive-typography** (47★) — textbook slope-formula `clamp()` generator with worked example, CSS custom properties, Tailwind config, and a JSON design-token export. Width-only (320–1200 default range), no a11y section, no verification, no tooling beyond the generator snippet. Competent but generic — same shape as wshobson/patricio0312rev.

**Other candidates (install/star counts only, not fully read):** yonatangross/orchestkit@responsive-patterns, josiahsiegel/claude-plugin-marketplace@tailwindcss-advanced-design-systems, onewave-ai/claude-skills@typography-scale-builder, oerlellijk/design-system-skill@flex-grid-flow, kylezantos/responsive-craft — all in the low-tens-to-low-hundreds install range per the original `npx skills find` listing, no outlier signal suggesting they'd break the pattern above.

**Did any agent skill account for viewport height in its fluid formula? No.** Every skill that touches height units (lvtd-llc, impertio-studio) uses `svh`/`lvh`/`dvh` exclusively for full-viewport hero sizing (`min-height: 100svh`), never blended via `min()`/`clamp()` with width into a shared type/space scale. Our `min(100svh/900, 100vw/1440)` coupling has no analog in any skill surveyed.

## Part 2 — Libraries and systems

See table above for the condensed comparison. Narrative notes:

- **Utopia** (utopia.fyi) is the field's reference implementation: two-anchor-point `clamp()` interpolation, rem-anchored, with per-step WCAG-violation flags in its calculator output and an explicit acknowledgment of Roselli's zoom critique in its blog. Purely width-driven — confirmed directly from `utopia.fyi/blog/clamp/`, no `vh` term anywhere in its formulas.
- **fluid-tailwind** is the only tool in the whole survey (skills or libraries) with a **compile-time WCAG 1.4.4 checker** (`checkSC144`, opt-out-able) — the strongest built-in a11y tooling found anywhere in this research.
- **postcss-px-to-viewport** converts px to `vw` *and* `vh` but as two independent, unbounded, uncapped conversions against a notional fixed design resolution (common in Chinese mobile-web dev for "design at 750px, scale to any screen") — not a coupled `min(vw, vh)` scale, and explicitly called out by multiple sources as zoom-hostile since it has no clamp floor/ceiling at all by default.
- **Open Props** and **Every Layout** are both width-only `clamp()`, both capped, neither ships a11y tooling.
- **Finsweet Client-First** is the most interesting counter-case: a mainstream, widely-adopted (Webflow-ecosystem-standard) methodology that **explicitly rejected vw/vh scaling** in favor of rem + root-font-size breakpoint scaling, marketing "browsers can zoom normally" as a core differentiator against exactly the class of system ours belongs to.
- **Agency vw-root pattern** (Lumos/Timothy Ricks and the generic `html{font-size:calc(100vw/1440*10px)}` idiom used across Awwwards/creative-agency sites) is the closest sibling to our approach in spirit — pure viewport-width-driven, unbounded until a hand-added freeze breakpoint — but confirmed width-only; no source found pairing it with height.
- **No system found — of ~11 libraries and 7 skills read in full, plus targeted searches for `min(vw, vh)` / "svh clamp design system" patterns — combines viewport height into the same fluid formula as width.** This appears to be a genuinely uncommon (not found elsewhere) technique, not merely under-documented; postcss-px-to-viewport's separate vh conversion is the nearest miss, and it's architecturally different (independent axis conversion, not a shared `min()`).

## Part 3 — Accessibility: WCAG 1.4.4, browser zoom, and our system

**Sources:**
- Adrian Roselli, ["Responsive Type and Zoom"](http://adrianroselli.com/2019/12/responsive-type-and-zoom.html) (2019): "When people zoom a page, it is typically because they want the text to be bigger. When we anchor the text to the viewport size... we can take away their ability to do that." Recommends avoiding `vw` for primary sizing, or mixing with `rem`/`em`, and testing to 200%+.
- Smashing Magazine, ["Addressing Accessibility Concerns With Using Fluid Type"](https://www.smashingmagazine.com/2023/11/addressing-accessibility-concerns-fluid-type/) (2023): confirms "browsers do not scale viewport-based units when zooming the page," and establishes an empirical **max ≤ 2.5× min** ratio as the threshold below which `clamp()`-based fluid type reliably passes WCAG 1.4.4 across browsers even at high zoom.
- fluid-tailwind [issue #11](https://github.com/barvian/fluid-tailwind/issues/11) and its `checkSC144` feature independently corroborate the same "browsers don't scale viewport units on zoom" mechanism, at the tooling level.
- Utopia's [clamp blog post](https://utopia.fyi/blog/clamp/) cites Roselli directly and forces text (not space) values to stay `rem`-anchored "for accessibility reasons."
- impertio-studio's skill states a related but distinct heuristic: "MAX MUST be at least 2× MIN per WCAG 1.4.4," citing [MDN clamp()](https://developer.mozilla.org/en-US/docs/Web/CSS/clamp).
- Finsweet Client-First [docs](https://finsweet.com/client-first/docs/fluid-responsive): explicit accessibility-motivated rejection of vw/vh scaling; "Browsers can zoom normally," "Browser font size settings that are modified by end-users will be respected."

**Mechanism (why vw cancels zoom on desktop).** Desktop browser zoom (Ctrl/Cmd+) rescales rendering by a factor *k* while simultaneously shrinking the CSS-pixel layout viewport by the same factor *k* (a 1440px-wide window's layout viewport becomes ~1024 CSS px at ~140% zoom, ~720 CSS px at 200%). A length fixed in `rem`/`px` keeps the same *computed* CSS-px value regardless of zoom, so the *k*× rendering scale makes it visibly larger. A length computed from `vw`/`vh` recomputes smaller by exactly 1/*k* as the viewport shrinks, and that shrink exactly cancels the *k*× rendering scale — so a pure-`vw` (or pure-`vh`) length renders at an **identical physical size at every desktop zoom level**. This is the crux of Roselli's and Smashing's findings, both confirmed independently above.

**VERDICT — our system at 200% zoom on a 1440×900 window.**

1. `--fluid = max(0.58px, min(100svh/900, 100vw/1440))` has **no `rem` term at all** above the 1024px breakpoint. Every clamp()-based system surveyed in Part 2 mixes a `rem` baseline into its "preferred" expression (`baseline_rem + slope·vw`), which gives *partial* zoom responsiveness — the rem term still grows physically even while the vw term cancels. Our formula has zero such mixing: it is **100% viewport-derived**, so it is a *strictly worse* case than the systems the accessibility literature already worries about. From 100% up to roughly 140% zoom (see below), rendered type size is exactly flat — not "slower-growing," literally unchanged in physical size.
2. The 1024px `lg:` breakpoint gate is itself a `min-width` media query, evaluated against the same shrinking CSS-px layout viewport. Solving `1440 / k = 1024` gives `k ≈ 1.406` — at roughly **141% zoom** (on a 1440-wide window), the layout viewport crosses below 1024px CSS width, the media query flips, and the page falls out of the fluid-scaled zone into the flat, per-breakpoint mobile CSS. That mobile CSS is ordinary fixed `rem`/`px`, which **does** respond normally to further zoom (it isn't itself zoom-broken).
3. So at 200% zoom specifically: yes, the user has already fallen through to the mobile layout (200% > 141% threshold) and text **does** enlarge from that point — but only because zoom pushed them out of the fluid system entirely, not because the fluid system itself responds to zoom. This is an *accidental* safety net, not a designed one, and it is inconsistent: the zoom level at which the net catches a user is `1024 / viewport_width_px`, so it scales **inversely with monitor width**. A user on our 1440px reference falls through at ~141%; a user on a 1920px monitor needs ~188%; a user on a 2560px ultrawide needs ~250% before text starts growing at all — a materially worse gap for exactly the large-desktop audience the 1440×900 reference targets. A user already on a ≤1024px-wide window (small laptop) gets essentially zero fluid-zone zoom dead band.
4. Mobile pinch-zoom is a different, unrelated mechanism: it scales the **visual viewport** only, leaving `window.innerWidth`/the CSS layout viewport (and therefore `vw`, `svh`, and media queries) untouched — it's optical magnification of whatever was already rendered, with no vw-cancellation effect, and no breakpoint-flip effect either. Since our system is flat CSS below 1024px anyway, mobile pinch-zoom is a non-issue for us either way — consistent with the general finding that this whole failure mode is desktop-browser-zoom-specific, not a mobile concern.
5. Bottom line, stated plainly: **our system fails the spirit of WCAG 1.4.4 more completely than the systems the accessibility literature already flags**, for any desktop user who zooms by less than roughly 40–150% (depending on window width) before hitting the breakpoint fallback. It is not a hypothetical edge case — 125%/150% browser zoom are the exact levels most commonly tested for low-vision users, and both sit inside the dead zone for our 1440px reference case. The unbounded-max design choice is irrelevant to this specific failure (it's a MIN-not-growing problem, not a MAX-too-small problem) — removing the ceiling does not fix, and was never going to fix, this.

## Insights: where we're stronger/weaker than the field

1. **Genuinely novel differentiator confirmed**: no agent skill (7 read) or library (11 covered) found couples viewport height into the same fluid formula as width via `min()`. Every height-aware unit found elsewhere (svh/lvh/dvh) is scoped to single-axis hero sizing, never blended into a shared type/space scale. This claim survives scrutiny.
2. **We are weaker on WCAG 1.4.4 than the field's own acknowledged weak point.** The literature's standing complaint about vw-based fluid type is that it *partially* defeats zoom; ours has no rem term at all above 1024px, so it *fully* defeats zoom in that range, and only recovers by accident when zoom pushes the layout below the breakpoint — a recovery threshold that gets materially worse the wider the user's monitor.
3. **No system surveyed ships fully unbounded (no-ceiling) fluid type as the *default*.** Utopia, fluid-tailwind, tailwind-clamp, Open Props, every agency vw-root pattern all cap explicitly. Ours is the outlier in leaving the top open by default — reasonable for a bespoke marketing site with controlled content and no user-generated scale-up needs, but it means we have zero of the built-in "MAX ≥ 2×/2.5× MIN" self-check the more mature libraries treat as table stakes (moot for the ceiling itself, but the absence signals no a11y-oriented ratio thinking went into the system at all).
4. **fluid-tailwind's `checkSC144` is the standout piece of tooling in the entire survey** — a compile-time gate that fails a build if a fluid value would violate 1.4.4. Nothing in our system does this; it's the single most actionable gap to close, and it's cheap (it's a ratio check + zoom-independence check, not new infrastructure).
5. **Damped dual-unit shrink (display/copy) has no direct analog** in anything surveyed. Utopia comes closest conceptually (different min/max per named step), but every library treats each named size as an independently-authored two-point interpolation, not a shared base unit with per-category damping curves. This is a structurally different, more systemic idea than "pick per-step min/max by hand."
6. **Tailwind v4 `@utility fluid-*` families are ahead of the pack ergonomically.** Most Tailwind fluid plugins (tailwind-clamp, tailwindcss-fluid-typography) still require arbitrary-value syntax or config-time enumeration; ours generates a systematic utility family from one base unit, closer in spirit to Open Props' token approach but wired natively into Tailwind's utility generation.
7. **We have no analog to Client-First's or the a11y literature's core recommendation** (mix in `rem`, respect user font-size) — this is a deliberate, documented choice per our own skill description ("deliberately ignores browser font-size above 1024px"), but it puts us on the opposite end of the spectrum from a widely-adopted, explicitly accessibility-motivated mainstream methodology (Finsweet Client-First), not just an obscure one.
8. **The mobile fallback (`flat, non-scaled CSS below 1024px`) is an accidental accessibility asset, not a designed one.** It happens to make the site correctly zoomable once a user's effective CSS viewport drops under 1024px, but the threshold for that fallback shifts with monitor width in a way nobody appears to have reasoned about (see Part 3 verdict §3).
9. **No agent skill in the field's SKILL.md corpus enforces a build-time or review-time check comparable to `checkSC144`.** jakubkrehel's `better-typography` has the best-structured *review process* (severity levels, Block/Approve gate) but applies it to wrapping/hierarchy/truncation, not to fluid-scale zoom compliance specifically — there's a clear opportunity to borrow that skill's reporting format and marry it to fluid-tailwind's actual check.
10. **impertio-studio's skill is the most technically current single artifact found** (MDN-cited, dated verification, explicit svh/lvh/dvh decision tree, hard-coded WCAG ratio rule) despite being nearly unstarred (1★, brand new) — star count is a poor proxy for skill quality in this space; several of the highest-install skills (per the original `npx skills find` listing) turned out to be the shallowest on inspection.
11. **"Unbounded upward" is a design-system positioning choice, not an accessibility feature**, and should not be described as one — it solves for large/ultrawide monitors looking intentional rather than letterboxed, which is an aesthetic/brand goal, orthogonal to (and in this survey, unrelated to) the WCAG 1.4.4 question, which is entirely about the MIN side and zoom, not the MAX side.
12. **If height-awareness is kept as the headline differentiator in any external-facing writeup, it should be paired with the 1.4.4 finding rather than presented alone** — "no one else ties type to height" is true and interesting, but immediately invites "does that make the zoom problem better or worse," and the honest answer (worse, see Part 3) should be part of the same pitch, not a follow-up someone else discovers.
