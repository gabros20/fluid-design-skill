# fluid-design: who runs it, how it ships

Design and plan for the last open items of v2: distribution (the binary question), the
path for people setting it up without an agent, automation, and the remaining tooling gaps.

## 1. Audiences

| # | Who | Where they are | What they need |
|---|---|---|---|
| A | **An agent using the skill** (Claude Code, Codex, Cursor…) | the skill folder is on disk | `node <skill>/bin/fluid …`, non-interactive, deterministic output, exit codes. Works today. |
| B | **A developer by hand, in a Node project** (Next, Vite, Astro, Remix…) | a terminal in their repo | one familiar command (`npx … init`) that asks a few questions, then plain CSS variables to tune. No agent, no skill folder. |
| C | **A developer in a project without Node** (Rails, Django, Laravel/Blade, Phoenix, Hugo, plain HTML), CSS or SCSS stack | a terminal, no `node` | a single executable, like Tailwind's standalone CLI. |
| D | **Automation**: CI, scaffolders, templates, dotfiles | a script | every question answerable by a flag, `--yes` for defaults, stable exit codes, a check that fails the build on drift. |

A is the primary audience and must not get worse. B is the largest human group. C is small
but real: the `css` and `scss` stacks exist precisely for projects without a JS build, and
Tailwind has shown that audience wants a standalone binary. D is the other side of B: every
interactive answer is a flag.

## 2. The binary question: decision

**Ship both: npm is the main channel, standalone binaries are the no-Node channel.** One
source (`skills/fluid-design/scripts/cli/index.mjs`), three ways to run it:

| Channel | Command | For | Built by |
|---|---|---|---|
| skill folder | `node <skill>/bin/fluid init` | A | already there |
| npm | `npx fluid-design-cli@2 init` | B, D | `npm publish` from the repository root |
| standalone | `curl -fsSL …/install-cli.sh \| sh`, then `fluid init` | C, D | `scripts/dev/build-bin.mjs` (`bun build --compile`), attached to GitHub Releases |

Why:

- **npm first.** Every project in audience B already has Node, and `npx <pkg> init` is the
  install gesture people know from shadcn, Storybook and Prisma. The CLI has zero
  dependencies, so `npx` fetches one small tarball. The package name is `fluid-design-cli`
  (`fluid-design` is taken on npm), and the command it installs is still `fluid`.
- **Standalone binaries for C**, built with `bun build --compile`. Bun cross-compiles all five
  targets (darwin-arm64/x64, linux-x64/arm64, windows-x64) from one machine. The binaries are
  64 MB (macOS arm64) to 99 MB (Windows), because each one carries the Bun runtime. That's the
  same order as Tailwind's standalone CLI. **Node SEA was
  rejected**: it needs the target platform's own Node binary to inject into, so it can't
  cross-compile. **`deno compile` was rejected** because its binaries are bigger for no gain.
- **Commands that need a browser** (`verify`, `probe`, `explain --url`) use Playwright.
  Playwright is a Node library that has to be installed in the project, so those commands stay
  Node-only. The binary says so and prints the `npx` command to run instead. Everything else,
  meaning init, generate, check, settings, explain, migrate, calc and audit, works in the binary.
- **Releases are CI, not a laptop.** A tag `v2.x.y` runs the tests, builds the five binaries
  plus `SHA256SUMS`, attaches them to the GitHub Release and publishes to npm, if an
  `NPM_TOKEN` secret exists. `install-cli.sh` picks the right asset, checks its sha256 and installs
  to `~/.local/bin`, or to `$FLUID_INSTALL_DIR` if set.

What the binary needs from the code:

1. **No reads of skill files at runtime.** The runtime (`assets/runtime/*`) is embedded as a
   generated module, `scripts/lib/emit/runtime-assets.mjs`. `generate-fluid.mjs` writes it and
   `--check` fails on drift, the same way as every other generated file.
2. **No child processes for tools.** The CLI imports `calc`, `probe`, `verify` and `audit` in
   process instead of spawning `node script.mjs`, because inside a binary `process.execPath` is
   the binary itself.
3. **One entry,** `export async function main(argv)`, which `bin/fluid` and the compile entry
   both call.
4. **Version pinning.** The lock file already records the version that generated it.
   `fluid check` warns when the running CLI is a different version: "generated by 2.0.0, this is
   2.1.0: run fluid generate". That way a CI `npx fluid-design-cli@2 check` can't silently
   disagree with a teammate's binary.

## 3. Without an agent: interactive `fluid init`

**Rule: prompts only when stdin is a TTY and `--yes` is absent.** An agent's shell is not a
TTY, so audience A sees today's behaviour unchanged.

The questions are the preflight decisions a human can answer. Each one shows its detected
default, and Enter accepts it:

| Question | Default | Flag | Lands in |
|---|---|---|---|
| Styling stack | detected from package.json | `--stack` | config `output.stack` |
| Framework | detected | `--integration` | config `output.integration` |
| Global stylesheet | detected path | `--css` | the import and settings go here |
| Existing site with its own base styles? | no, or yes if the stylesheet already has an `html`/`body` rule | `--brownfield` | config `output.base` |
| Desktop artboard (design frame) | `1440x900` | `--desktop 1440x900` | settings `--fluid-desktop-base-width/height` |
| Desktop starts at | `1024` | `--desktop-at 1024` | config `bands.desktop.minWidth` |
| Scale below desktop too? (phone, tablet, landscape) | yes | `--no-mobile` | config `bands.*` |
| Phone artboard width | `390` | `--phone 390` | setting `--fluid-phone-base-width` |
| Page max width | `1680` | `--max-width 1680` | setting `--fluid-desktop-container-width` |

- **Any setting** can also be passed as `--set --fluid-desktop-scale-max=1.4`. The flag
  repeats, and each value is validated against the spec.
- **Answers that are settings** are written as real declarations into the `:root` starter, not
  as comments. Only values that differ from the default are written.
- **Answers that are structure** go into `fluid.config.json`.
- **At the end, init prints what it did** and the next three commands.

Around init:

- **`fluid generate --watch`** regenerates whenever `fluid.config.json` changes, for people
  editing the structure by hand while the dev server runs.
- **CI:** `npx fluid-design-cli@2 check` exits 1 on any problem: schema, settings lint,
  hand-edited output, a stale lock, or a version mismatch. The README gives a ready GitHub
  Actions step.
- **A human reference:** the root README gets a "Without an agent" section: install, init,
  tune, check. `SKILL.md` stays the agent's document.

## 4. Remaining tooling gaps: decisions

| Gap | Decision |
|---|---|
| `explain --at <selector>` | With `--url`, it measures and reads settings on that element, not on `:root`, so a header limited by `fluid-grow-until-1680` shows its own numbers. Offline, `--set` does the same what-if without a browser: `fluid explain 1920x1080 --set --fluid-grow-until=1680`. |
| A limit with nothing to limit | `explain --url` lists every scope on the page (limit utilities, `.fluid-scope`, `[data-fluid-scope]`), with its values and the number of fluid-sized elements inside. A scope with zero gets a warning. This is a DOM check rather than a static lint, because only the rendered tree knows what a component contains. |
| SCSS limit mixins untested in a browser | The SCSS module is compiled with `sass` in a new browser test, rendered in Chromium, WebKit and Firefox, and compared with `evaluate()`. It covers the functions, band mixins and every limit mixin. |
| The examples don't show the new features | pizza-next: the site header stops growing past a 1680 window through `:root { --fluid-ui-grow-until: 1680 }`, the form `fluid check` recommends for a header because it holds `--header-h` too. Its wordmark subline uses the band variant `fluid-landscape:hidden`. pizza-vite-gsap: the footer is a subtree limit, `@include fd.fluid-ui-grow-until(1920)`. Both are re-verified in 3 browsers. |
| scroll-animation's mirror of `fluidPx` | Adds the `el` parameter, and the docs mention that a limited subtree reads its own units. |
| Evals 5 and 6 never run | Run each once with the skill, on a fixture project, and grade with a script. |
| Zed | Researched; see below. |

## Zed

**Class autocomplete works.** Zed runs Tailwind's own language server
(`tailwindcss-intellisense`), which loads the real v4 engine, so the `fluid-*` `@utility`
classes and their `--value()` suggestions are listed the same way as in VS Code. Source:
zed.dev/docs/languages/tailwindcss.

**Settings autocomplete in CSS files is unverified.** Zed's CSS server is
`vscode-css-language-server`. That server reads custom data from the `dataPaths`
initialization option, which is what VS Code's `css.customData` becomes (microsoft/vscode#79599).
No Zed doc or issue confirms that Zed passes this option through, so this snippet is untested:

```json
// .zed/settings.json
{ "lsp": { "vscode-css-language-server": { "initialization_options": {
  "dataPaths": ["src/styles/fluid/fluid.css-data.json"] } } } }
```

`fluid init` doesn't write it, because we couldn't verify it. The settings still validate in
`fluid check` whatever the editor.

## 5. Plan

1. CLI core for the binary: embedded runtime, in-process tools, `main(argv)`, version check.
2. Interactive init, the flags, `--set`, and `generate --watch`.
3. `explain --at`, `--set` and the scopes report.
4. `build-bin.mjs`, `install-cli.sh`, the release workflow, and npm packaging.
5. Tests: extend the CLI test (flags and scripted answers), a binary smoke test, and the SCSS
   browser test.
6. Examples, the scroll-animation mirror, and docs.
7. Evals 5 and 6, and the Zed note.

Not in scope, because it's the owner's call: publishing to npm, pushing and tagging a
release, and migrating the Eagle site.
