/fluid-design

A design is drawn on one frame, usually 1440×900. A normal build is exact there and wrong on every other window: cramped at 1280, floating at 2560, off the bottom of a 700-tall laptop. fluid-design writes every drawn number as number × one unit, 1px at the artboard, so the page is a proportional copy of the design at every size. Viewport-fluid layouts that scale as one drawing.

One design, many windows

The design is exact on one frame. The site is opened on every other one. Hand-typed pixel values, a max-w-7xl container and a few breakpoints fail in four predictable places:

1280×800cramps

A 1280-wide row drawn for 1440 has 160px less room. The heading re-wraps from three lines to four, then seven at 1024; the art overflows or crushes the column.

2560×1440floats

Fixed pixels do not grow. The 1440 composition sits small in the middle of a 5K display, a sea of margin on every side, type that reads like a footnote.

1440×700runs off

A "one-screen" hero drawn 900 tall is 200px past the bottom of a 13-inch laptop's window. The call to action and the section's closing beat land below the fold.

390×844redrawn

Below desktop, the phone design gets re-authored at sm:, md: and every width a device reports. Each breakpoint is a new drawing nobody designed.

Scaling type alone does not fix it: the layout has to take the width arm too, or the column never gets its room back. Measured on the reference build (a production marketing site this skill was extracted from), a drawn 64px, three-line heading:

The unit: n × --fluid

There is one measured unit. --fluid is 1px at the artboard and follows whichever window axis is tighter. Every drawn number becomes that number times the unit, so the whole page shrinks and grows against one shared factor, and the design's proportions hold by construction. There is no table of per-property clamp() pairs to keep in sync.

--fluid = max( 0.58, min( W / 1440, H / 900 ) )
W / 1440 the width arm H / 900 the height arm, in svh min() contain, never cover 0.58 --fluid-desktop-scale-min no ceiling --fluid-desktop-scale-max unset
Tailwind v4lg:fluid-py-120
CSScalc(120 * var(--fluid))
SCSSfd.fluid(120)
StyleXfluid(120)

  • purely proportionalNo intercept on either arm, so 900 × --fluid = 100svh whenever height binds. The artboard is a viewport, not the container.
  • svh, never dvhdvh resizes type while the reader scrolls. Pinned layers use lvh, and their cancelling margin uses the same unit.
  • one scale per pageChange how a part scales with a limit or a setting on a scope, never by redeclaring --fluid: the type units would not follow.
  • the number is unitless64px * var(--fluid) is invalid and drops the declaration silently. Write the drawn number, never a converted one.
  • off the scale on purposeBorder and stroke widths, em tracking and text measures stay fixed. Radii scale with their box (fluid-rounded-*).
  • generate, never hand-writeThe output encodes measured numbers (the ×1000 precision form, the knee, the zoom thresholds). fluid generate refuses to overwrite a hand-edited file.

Type roles, damping and the knee

A heading shares its column with fixed measures, so type shrinks more gently than the layout. --fluid-display and --fluid-copy (plus any role you add, such as caption) read the same unit through a per-band damping curve. Above the artboard they grow with it one to one. Plotted from the engine's formula at the desktop defaults:

--fluid · layout--fluid-display · damping 0.62--fluid-copy · damping 0.33the knee
--fluid 0.7778 (1440×700) → a drawn 64 heading renders 55.2px on display, 18 copy renders 16.7px, a 120 padding is 93.3px

--fluid-display = max(--fluid, d · max(--fluid, knee) + (1 − d)). The knee is the unit at the band's lower edge (1024 / 1440 = 0.711). Below it, on a short desktop window where the layout keeps compressing toward 0.58, headings hold at the size they had there, so they stay readable while the section still fits.

Limits, scopes and the container

Sometimes part of a page should stop scaling: a header that stops growing past a 1680 window, a panel that never shrinks below its 1280 size, a widget that should not scale at all. That is a limit, one utility on the element, in window px. It makes the element a scope, and every fluid-* class inside it follows. On a tall window (width binds):

defaultfluid-grow-until-1680fluid-shrink-until-1280fluid-off

fluid-grow-until-1680

Units stop growing: they keep the size they had at a 1680 window. Writes --fluid-grow-until: 1680.

fluid-shrink-until-1280

Units stop shrinking below their 1280 size. Overrides fit-height, so use it on components, not one-screen sections.

fluid-ui-grow-until-1680

Only --fluid-ui stops growing. For the site header, set it on :root so --fluid-header-h holds with it.

fluid-off

Nothing scales inside: one drawn px is one CSS px. Browser zoom still works.
  • they composeThe innermost limit wins, fluid-off beats a limit on the same element, and lg:fluid-grow-until-1680 limits only from lg. A limit applies only in the band that contains its width.
  • any setting, any subtreeclass="fluid-scope" (or data-fluid-scope) plus a setting gives one section a different container, damping or scale-min. Every unit recomputes together there.
  • scopes are listedfluid explain --url lists every limited subtree on a live page with what inside follows the scale, and flags a limit with nothing fluid inside.
  • the header trapA limit class on <header> drifts from --fluid-header-h on :root. Use :root { --fluid-ui-grow-until: 1680 }; fluid check warns on the class.

fluid-containerone per section

  • The page wrapper: max width 1680 drawn px and side padding 80 on desktop, 560 / 24 on the mobile bands, both from the active band.
  • The max width only grows: at 2560×1440 it is 2688px, never narrower than 1680 CSS px.
  • Apply it once per section, on the section's inner wrapper. A text measure sits inside it and never replaces it.

the content budgetcheck before building

$ fluid calc budget --widths 600,120,560 row: 600 + 120 + 560 = 1280 budget at the artboard: min(base-width 1440, container-width 1680) − 2 × padding 80 = 1280 PASS — 0px to spare.
  • A row over budget is a drawing problem or a cqw problem. A smaller padding never fixes it.

Structure vs settings

Configuration has two halves that change at different speeds. Structure decides which CSS rules exist and lives in a small JSON file. Settings are every number, and they are CSS variables registered with @property defaults, set in your own :root next to your tokens. This is the file fluid init wrote for a Next + Tailwind v4 project, and the :root it edited:

fluid.config.jsonstructure

{ "$schema": "./fluid.config.schema.json", "version": 2, "bands": { "phone": true, "tablet": { "minWidth": 600 }, "landscape": { "maxHeight": 500 }, "desktop": { "minWidth": 1024 } }, "output": { "integration": "next" } }
  • Which bands exist and their breakpoints, the role names (add "caption"), the prefix, ui and zoom on or off, the output stack and folder.
  • Validated by fluid.config.schema.json in your editor.
change it → fluid generate (or keep generate --watch running)

your :root43 settings

@import 'tailwindcss'; @import '../styles/fluid/fluid.css'; :root { --brand: #796100; /* fluid settings — every one, with its default, is in ../styles/fluid/settings.reference.css */ --fluid-phone-scale-min: 0.8; --fluid-desktop-display-damping: 0.7; --fluid-desktop-scale-max: 1.4; }
  • Artboard widths, scale min and max, damping per band and role, the container, header heights, limits, the zoom text range.
  • An invalid value falls back to its default; fluid check flags a typo with a suggestion. fluid.css-data.json autocompletes them in CSS files.
change it → nothing to run: live, no regenerate

One import brings the units, the settings, the base layer, the breakpoints, the band variants and the utilities. Everything is generated into one folder (src/styles/fluid/ by default): fluid.css, base.css, settings.reference.css, fluid.ts, cn.ts / _index.scss / fluid.stylex.ts, runtime/, integrations/, README.md. The decisions are logged in a short FLUID.md. Every key and setting with its default: config.md.

Four stacks, one set of units

Every stack spends the same custom properties, defined once in the generated fluid.css; only the authoring surface differs. The same hero, four spellings:

<section class="fluid-py-48 lg:fluid-py-120 lg:fluid-h-900"> <div class="fluid-container"> <h1 class="fluid-display-40/44 lg:fluid-display-64/72">…</h1> <p class="fluid-copy-16/24 lg:fluid-copy-18/28">…</p> </div> </section>

The phone number unprefixed, the desktop one behind lg:. Bare numbers in 0.25 steps, anything else bracketed (fluid-p-[8.3]); /lh is drawn px, not a ratio. Components that take className need a cn that knows the fluid classes: keep yours and extend it with withFluid.

.hero { padding: 80px 24px 40px; } @media (min-width: 1024px) { .hero { padding-block: calc(120 * var(--fluid)); height: calc(900 * var(--fluid)); } .hero h1 { font-size: calc(64 * var(--fluid-display)); line-height: calc(72 * var(--fluid-display)); } }

Plain var() inside each band's media query, plus one class, .fluid-container. CSS Modules is the same stack. Classic min-width syntax keeps your own queries at the Safari 15.4 floor.

@use 'fluid' as fd; .hero { @include fd.fluid-desktop { padding-block: fd.fluid(120); @include fd.fluid-type(64, 72); } }

Functions (fd.fluid(), fd.fluid-display(), fd.fluid-ui()…) and exclusive band mixins on top of the same fluid.css. The functions @error on a number that already has a unit, so the silent 64px * var(--fluid) failure becomes a build error.

import * as stylex from '@stylexjs/stylex' import { fluid, fluidDisplay } from './styles/fluid/fluid.stylex' const s = stylex.create({ hero: { paddingBlock: { default: '40px', '@media (min-width: 1024px)': fluid(120) } }, title: { fontSize: { default: fluidDisplay(40), '@media (min-width: 1024px)': fluidDisplay(64) } }, })

Typed helpers that return calc() strings, plus fluidContainer as a style object. The units stay plain global CSS: StyleX's defineVars cannot express a variable whose formula reads a sibling, which every unit does. The media key is DESKTOP_QUERY from fluid.ts.

What it is, and what it isn't

This skill makes the page the right size. It contains no animation.

fluid-design

  • "Match our 1440 Figma frame at every laptop size", "fit one screen"
  • "The page floats on 2560", "the header is huge on 5K"
  • "The hero doesn't fit on a 13-inch laptop"
  • Converting an existing site, or a v1 fluid-design project
  • What the scale has to survive: iOS Safari viewports, media sizing, browser zoom, a stale stylesheet

not this skill

  • Motion: triggered entrances, pinned and scrubbed scenes, scroll wells, video playback, GSAP and Lenis coexistence. That is scroll-animation.
  • A breakpoint ladder with clamp() type (Utopia-style "make it responsive"): a different model, one pair per property.
  • A colour system or a component library. The tokens reference covers only where tokens live next to the settings and the traps that compile clean.

Each works alone. Together they meet at three points, all owned here (contract.md §7):

--fluid-header-hthe fixed header's resting height: anchor offsets, sticky tops and header-ink probes read it
translatefluid-translate-* writes translate, so Motion's transform composes with it; drawn travel scales through fluidPx()
